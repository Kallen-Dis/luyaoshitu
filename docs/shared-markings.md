# 共享标注设计

[返回 README](../README.md) · [算法设计](algorithm-design.md) · [报告设计](report-design.md)

共享标注用于补充地图未及时收录的现场信息。它不是允许任意用户直接改全体用户的算法结论，而是将“提交、核实、采用、影响”分开记录。

## 1. 四类信息及其作用

| 类型 | 提交内容 | 分析时的作用 |
| --- | --- | --- |
| 围挡 / 封路 `closure` | 中心、半径、施工 / 封路 / 门禁等种类 | 加入本次围挡集合，检查路线与设施是否受影响 |
| 设施失效 `facility_missing` | 类别、名称、位置、关闭 / 不开放 / 错位 / 不售菜等原因 | 按匹配规则剔除或修正对应设施 |
| 补录设施 `facility_extra` | 类别、名称、位置，可附明确售菜确认 | 添加候选，再按路网测距，不能直接算已覆盖 |
| 灰色区域 `gray_area` | 多边形、缺少品类、服务质量或容量等原因 | 作为人工反馈层展示，不直接覆盖算法盲区 |

围挡当前用圆近似；人工灰色区域用多边形。几何统一 BD09，接口中的多边形坐标为 `[经度, 纬度]`。

实现：[models.py](../backend/app/markings/models.py)、[apply.py](../backend/app/markings/apply.py)。

## 2. 数据与存储

规范化后的 `spec` 是标注内容的权威记录；代表点、外接框、类别等索引字段从它推导，服务附近检索。主要数据包括：

- 标注 ID、类型、来源、内容、状态、当前版本、创建 / 更新时间及有效期。
- 设备标识哈希、编辑令牌哈希；公开响应不返回原始身份或编辑凭证。
- 每一版内容快照，以及提交、修改、撤回、恢复、审核、照片处理等事件时间线。
- 照片记录、文件摘要、尺寸、公开 / 隐藏状态与上传关系。
- 确认 / 异议票，设备的重复投票以更新或撤回处理。

SQLite 与照片默认放在 `data/user/`，可通过 `MARKINGS_DIR` 更改。它们是用户数据，不是可随意清理的 API 缓存，不进 Git；备份应覆盖数据库、照片和部署使用的身份盐。

实现：[store.py](../backend/app/markings/store.py)、[service.py](../backend/app/markings/service.py)。

## 3. 提交、版本与有效期

提交链路：

```text
填写信息 → 上传至少一张现场照片 → 引用预上传照片 ID
       → 服务端字段 / 几何 / 照片校验 → 事务创建待核实记录
       → 返回标注与一次性编辑令牌 → 页面保存管理凭证
```

预上传照片与设备绑定；失效、重复或他人的上传不能随意挂到新记录上。服务端校验文本长度、经纬度、半径、多边形面积、跨度、自交与折返尖刺，不仅依赖前端限制。

当前默认约束包括：围挡半径 10–300 米；人工区域至少 400 平方米、至多 1 平方公里、跨度不超过 3 公里；有效期允许 7–365 天。类型相关默认有效期由后端统一下发：施工 60 天、临时封路 30 天、门禁 / 断路 365 天，设施类 180 天，人工区域 365 天。

修改需要当前 `version` 和编辑令牌。版本过旧返回冲突，要求刷新，避免后写入者覆盖别人刚完成的处理。内容修改会产生新版本；已核实内容修改后重新待核实。回到旧内容也产生新版本，不能抹掉中间历史。

撤回保留可追溯记录，可以恢复；恢复时按此前状态和有效期规则处理。有效期在读取时判断，过期内容不再进入有效分析集合，不依赖定时任务才能失效。

## 4. 身份、投票与管理员审核

当前采用轻量身份：浏览器生成设备 ID，服务端存加盐哈希；新建时另发随机编辑令牌，后续修改 / 撤回 / 恢复须提交该令牌，服务端只存哈希并做恒定时间比较。

**设备 ID 不是完整账号认证。** 更换设备或清空存储可能失去编辑凭证，也不能据此彻底防止刷票。面向大规模公开服务时，仍应补充账号、权限与滥用控制。

状态流转以 `pending` 待核实为起点。管理员可以核实、驳回、归档或重新打开；作者可以撤回。过期是按当前时间推导的有效状态。

管理员接口通过后端 `ADMIN_TOKEN` 鉴权；未配置有效口令时审核关闭。同一设备不能核实自己提交的记录。核实要求先打开当前版本详情、经过最短查看时间、逐项确认位置 / 描述 / 时效并给出依据；采用照片依据时还要确认已查看相关照片。详情打开后内容又被修改，则需重新查看。审核和照片隐藏 / 恢复均留记录。

投票仅改变排序、置信提示及争议状态，**不会自动核实**。展示置信度采用 Beta 先验的均值形式：

$$
C=\frac{a+n_{confirm}}{a+b+n_{confirm}+n_{dispute}}.
$$

普通用户来源的先验为 $(1,1)$，已核实记录为 $(9,1)$，其他来源有各自先验。临近到期的围挡还会衰减展示置信度。异议至少比确认多两票时显示有争议。这是工程排序分数，不是校准过的真实概率，也不决定全体生效。

实现：[trust.py](../backend/app/markings/trust.py)、[routes.py](../backend/app/markings/routes.py)。

## 5. 哪些标注参与本次体检

| 模式 | 选择规则 |
| --- | --- |
| `auto` 默认 | 已核实的 + 自己的有效标注，并允许逐条采纳其他标注 |
| `all` | 也纳入他人待核实信息；仍受有效性、去重与数量限制 |
| `none` | 保留纯算法输入，附近信息作为建议展示 |

逐条排除优先于自动选择。未采用的记录应说明是建议还是被跳过，而不是悄悄消失。围挡默认总数最多 20 处，设施类标注单次最多 10 条；重复围挡合并，超限说明原因。

设施失效按品类、规范名称与位置匹配，默认匹配范围 50 米，避免删除同址其他门店。同一设施存在多条证据时，结合作者、审核状态和更新时间排序处理。原品类查询失败时不把人工记录当作检索已完整成功。

人工区域不改变算法网格缺失判断；补录设施必须测距，围挡必须经过路线关系检查。绕行线索是算法证据，不等于用户提交的围挡。

## 6. 基线对照与出行使用

分析先保留纯算法结果 A，再在采用标注后的输入上计算 B；相同测距可复用缓存，补录或换候选仍可能新增请求。结果记录采用标注的 **ID、版本、内容与影响**，支持回看纯算法 / 叠加标注的差异。

有标注并不意味着一定产生差异：远离路线的围挡可能没有影响；补录药店也可能仍超过步行阈值。报告应展示实际重算影响，不能把提交数量当成改善数量。

出行根据当前有效标注重建规划副本，过滤失效设施、应用围挡并保留已采纳信息；不把最新出行上下文直接写回旧体检历史。详见 [居民出行设计](resident-travel.md)。

## 7. 照片、隐私与接口保护

- 至少一张现场照片是提交证据要求，不能证明照片内容一定真实；地图位置仍会公开。
- JPEG / PNG / WebP 按文件内容识别并检查结构、大小与尺寸，当前单张上限 4 MiB。
- 前端重编码之外，后端继续去除 EXIF、XMP、文本和相关元数据；不因后缀正确就接受。
- 元数据清理不移除照片画面里的门牌、人脸或车牌，上传者仍需注意画面隐私。
- 文本去除控制字符，公开说明里的网址和电话号码替换处理。
- 写操作、投票和照片上传受限流；照片公开 / 管理员读取使用不同缓存策略。

主要接口位于 `/api/markings` 与 `/api/admin/markings`；支持附近检索、我的记录、详情、创建 / 修改、撤回 / 恢复、版本回退、投票、照片与审核。字段和当前限制以运行中的 `/docs` 及后端下发枚举为准，避免前后端维护两套值。

实现：[photos.py](../backend/app/markings/photos.py)、[routes.py](../backend/app/markings/routes.py)、[前端标注组件](../frontend/src/components/markings)。

## 8. 验证重点

1. 不能用别人的编辑令牌改标注，旧版本修改触发冲突。
2. 修改已核实内容后重新进入审核；投票不自动升级状态。
3. 过期、撤回、驳回与归档记录不误入默认计算。
4. 三种采用模式、逐条采纳 / 排除及冲突设施证据优先级一致。
5. A / B 对照可复现，采用版本与报告影响可追溯。
6. 伪装、超限、重复照片被处理；元数据清理和隐藏权限符合预期。

对应回归包括 [服务测试](../backend/tests/test_markings_service.py)、[叠加测试](../backend/tests/test_markings_apply.py)、[照片测试](../backend/tests/test_markings_photos.py) 和 [接口测试](../backend/tests/test_api_markings.py)。
