# 居民出行设计

[返回 README](../README.md) · [算法设计](algorithm-design.md) · [共享标注](shared-markings.md)

出行将体检发现的设施变成可查看的步行计划。它使用独立的规划副本与预算，不改变已经生成的生活圈、盲区和评分。

## 1. 使用流程与范围

```text
选择起点 → 选择一个品类或按顺序添加站点
        → 获取候选与入口 → 路网测距 / 排序或选组合
        → 取得路线、检查围挡 → 展示计划
        → 可换站、定位后重规划，或退出返回报告
```

起点可来自社区中心、地图点选、网格居民点，定位后还可从当前位置出发。网格起点需要尊重实测子格 / 继承父格的测量来源，不能仅因画面切成 50 米格就假称每个起点都已经测过。

候选来自分析中的设施列表，允许使用圈外设施；生活圈是社区统计范围，不是禁止居民走出去的边界。必要时可补检索，但必须记录补检索的预算和完整性。当前支持六类设施，站数上限由后端按品类数下发，不能继续沿用早期“最多三站”的描述。

离线模拟使用明确标注的估算设施与距离，不表示百度真实路线。规划模拟预览不能直接作为正式居民出行输入。

实现：[routes.py](../backend/app/trip/routes.py)、[service.py](../backend/app/trip/service.py)、[candidates.py](../backend/app/trip/candidates.py)。

## 2. 候选清洗与入口状态

设施使用稳定的位置、名称和品类标识，校门 / 导航入口是独立候选节点。同一学校的不同校门不能在不同路段之间无条件瞬移，也不能把它们计为多所学校。

默认排除失效、处于围挡内和不满足买菜能力规则的候选；用户明确查看待确认生鲜门店时，仍保留待确认说明。最新有效共享标注可修正规划副本中的候选与围挡。

检索失败、搜索被截断和旧快照完整性未知各自保留状态；排序只针对当前已检索的候选，不能宣称整个城市最优。

## 3. 最近设施：逐个补测与下界停止

目标是按真实步行距离返回最近若干家，当前最多五家。距离由矩阵接口提供；展示折线使用路线接口，二者职责不同。

设入口 $p$ 的经验下界为：

$$
L(o,p)=\max(0,d_{straight}(o,p)-\varepsilon),\qquad \varepsilon=30\text{ 米（默认）}.
$$

先按下界顺序测量候选。对同一设施的多个入口取已知最小步行距离，并继续考虑尚未测量入口是否可能改变排名。若已测第 $k$ 家距离为 $D_k$，剩余所有候选下界都不小于 $D_k$，可以在下界假设成立的条件下停止：

$$
D_k\le\min_{p\in\text{未测入口}}L(o,p).
$$

另一种完成方式是测完快照内所有相关候选。若出现实际返回距离小于下界，停止利用该下界证明排序；请求失败、预算用尽也不冒充排名已验证。

`ranking_verified` 表示规定范围和假设下的排序状态，不是“现场已营业”“一定卖菜”或“路线绝不会封闭”。响应还保留验证依据，区分全量候选和经验下界证明。

## 4. 固定站序的多站动态规划

用户决定先去什么、后去什么，例如“生鲜采买 → 基础教育 → 医药”。系统为每站选择设施和入口，**不自动调整品类顺序**。

将第 $j$ 站的入口候选组成一层 $V_j$，起点为 $o$，测得有向步行边权 $d(u,v)$。状态递推：

$$
F_1(v)=d(o,v),\qquad
F_j(v)=\min_{u\in V_{j-1}}\{F_{j-1}(u)+d(u,v)\}.
$$

最终从 $\min_{v\in V_m}F_m(v)$ 回溯入口序列。目标是总步行距离最小，不是总耗时最小；耗时另行展示。失败边未知，不能当零距离；反向边不直接复用正向距离。

若每层 $n$ 个入口、共 $m$ 站，完整相邻层边表约需 $n+(m-1)n^2$ 个点对，远少于枚举全部 $n^m$ 个完整组合，但仍可能超预算。因此先取有限宽度候选求可用解，再检查尚未排除的组合。

实现：[planner.py](../backend/app/trip/planner.py)。

### 4.1 惰性组合验证

先用相同逐边下界做后缀动态规划，计算从每个入口到最后一站的最小剩余下界。优先队列按：

$$
\text{组合下界}=\text{已选前缀下界}+\text{后缀最小下界}
$$

展开可能优于当前解的组合，缺哪条边才测哪条。只有剩余下界均不能改进当前解，或所有相关组合完成核验时，才能给出对应范围内的最优性说明。设置入队状态总数上限，防止大量近似相同下界耗尽内存；超限保留当前可用解并说明未完成最优性验证。

“找到一个计划”“取得全部路线”“排序 / 组合验证完成”是不同状态。

### 4.2 手动换站与通行约束

用户可以指定设施或固定某些站点，此时结果是手动选择或约束下的解。系统保留连续的同一入口坐标，重新检查相邻边，不能沿用换站前的距离。

有围挡时，可用性求解还要排除已知被阻断的组合；未取得路线或无法完成围挡核验的组合仍保留未核验状态。实现：[feasible.py](../backend/app/trip/feasible.py)。

## 5. 路线展示与状态分离

对选中的每一段取得步骤和折线，提取过街提示并核验围挡相交。矩阵排名不因另一接口返回了较漂亮的路线就悄悄改成另一种距离口径。

| 结果 | 含义 |
| --- | --- |
| `clear` | 各站路段连续，已取得所需路线与步骤，当前已知围挡检查通过 |
| `blocked` | 至少一段被已知围挡判为阻断 |
| `unverified` | 模拟估算、缺路线、段数 / 衔接不完整或核验未完成 |

`clear` 是当前地图和围挡数据下的系统状态，不保证实际所有道路都开放。路线请求失败时可保留已测距离，但不画一条直线冒充可走路线。离线估算的虚线必须说明口径。

实现：[status.py](../backend/app/trip/status.py)、[service.py](../backend/app/trip/service.py)。

## 6. 定位与沉浸式查看

页面可以查看路线起点、全路线并定位到自己。当前位置与原计划不同，需要用户选择：从当前位置前往原目的地、重选附近同类设施，或继续查看原计划。

定位精度不足时要说明，不能把不可靠定位自动当成精确起点。重规划会根据当前位置生成独立副本；同类附近检索是新请求，可能花配额。原报告与历史不随浏览器位置变化被覆盖。

售菜反馈可以记录近期用户观察，但与“已审核共享标注”“可通行”“排名最优”分别处理，不能只因一票反馈就静默改变全体覆盖结论。

实现：[guide.py](../backend/app/trip/guide.py)、[context.py](../backend/app/trip/context.py)、[feedback.py](../backend/app/trip/feedback.py)、[前端出行组件](../frontend/src/components/trip)。

## 7. 预算、缓存与隐私

出行与体检共享服务商总配额，以下是额外的项目保护预算，默认值见 [.env.example](../.env.example)：

| 资源 | 默认上限 |
| --- | --- |
| 测距点对 | 每日 500、每小时 120、单次 120 |
| 路线请求 | 每小时 200、单次 12 |
| 规划入口请求 | 每小时 120，缓存 / 模拟请求也计入口限流 |
| 补检索请求 | 每日 200、每小时 60、单次 48 |
| 组合搜索 | 最多 20000 个入队状态 |

重试计入实际调用预算；命中测距 / 路线缓存不增加百度调用。SQLite 事务保存跨重启、跨 worker 的出行计数，数据库只记时间与数量，不存起终点坐标。

中心起点可使用精确双端持久缓存；地图点选、方格和定位衍生行程使用内存缓存，避免将居民具体出发点长期写入磁盘缓存。预算不足时返回已完成部分、未验证说明和剩余额度，不擅自扩大预算。

实现：[budget.py](../backend/app/trip/budget.py)、[routing.py](../backend/app/trip/routing.py)、[supplement.py](../backend/app/trip/supplement.py)。

## 8. 验收

1. 最近五家按设施去重、入口取最优；失败候选不能被当作已经排除。
2. 小规模全量边表与动态规划结果一致，固定站序、固定站点和换站后连续性正确。
3. 下界失效、候选截断、预算用尽、搜索超限均停止宣称最优。
4. 距离已测但折线未取到时，排序与通行状态分别反映实际情况。
5. 最新围挡 / 失效标注生效，定位重规划不修改报告与历史。
6. 重试、缓存、并发预算和隐私缓存策略可回放检查。
