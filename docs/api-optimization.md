# 百度地图 API 调用优化报告

> 对应评分细则「API 深度调用与工程优化」（30%）的三项：计算策略与优化、容错与降级、创新的空间插值。
> 本文只写代码里已经实现、并且有实测数据的内容；每个数字都注明出处。第 4 节汇总接口能力边界的实测，第 5 节是已修的问题和剩下的不足。
> 系统整体设计见 [技术设计文档](design.md)。
> 2026-10-01 整理，2026-10-03 更新：盲区网格改为 15 分钟圈内 100 米；修掉矩阵补测重复请求、配额错误被吞两处问题；
> 数据换成重新生成的快照与零配额回放实验（[`reports/api-benchmark.md`](../reports/api-benchmark.md)）。
> 2026-10-04 更新：小学改按校门（导航点与出入口）测距，按标签剔除培训、成教类误检；两份快照与回放实验随之重跑，下文数字均为新版。

## 0. 一页结论

- **配额按点对计，所以优化的目标是"少用点对"，其次才是"少发请求"。** 实测同一天约 140 次批量算路请求、共 2479 个点对就触发了日配额（302），同日地点检索只用了 38 次。
- **批量算路**承担全部"测距离、测耗时"的工作，每个请求都尽量装满 100 个点对（起点数 × 终点数 ≤ 100）。等时圈 252 个采样点只发 3 个请求，中心到圈内 116~144 个网格只发 2 个请求。
- **盲区判定是最费点对的一环**，用三条措施压下来：直线下界剪枝、够近就停、按候选分组装箱。曹杨（圈内 144 格）现行 **746 个点对、51 个请求**；每格对每家都测要 **19584 个点对**，逐对请求要 18720 个请求。结论与全量测 99.3% 一致，其余 0.7% 记"未知"，没有一格判反。
- **小学按校门测距**：学校占地大，定位点可能落在没有校门的围墙边。小学改为测到最近的校门（地点检索 scope=2 返回的导航点和"出入口"子点，最多 4 个），曹杨小学盲区从 26 格降到 18 格，同时有 2 格从"达标"变成"盲区"，两个方向都有；桃浦没有格子翻转。代价是曹杨盲区一段从 652 个点对增加到 746 个（[`reports/school-gates.md`](../reports/school-gates.md)）。
- **缓存按点对存储**（坐标量化到 50 米，30 天有效），补测时**只请求缺的点对**。同一地点重跑 0 个点对。
- **并发**：令牌桶把总速率钳在 8 QPS（按点对数折算权重），批量算路最多 3 个在途、步行路线最多 4 个在途，连接复用。回放实验里在途 1 → 3，盲区一段耗时从 28.9 秒降到 14.4 秒。
- **耗时**：三档延迟假设下，现行做法的盲区一段只要全量矩阵串行的 4%~10% 的时间。
- **容错原则**：不把"没测到"写成"没有"。
  - 检索失败的品类标"查询失败"，不当 0；
  - 测距失败的网格记"未知"，不算盲区；
  - 采样整批失败就不出等时圈，不画一个缩水的圈；
  - 配额耗尽时立即熔断该接口，错误一路上抛，写明是哪个服务、何时恢复。
  - 注入 401 限流、网络中断、配额耗尽、检索失败四类故障，**没有一格被误判为盲区**。
- **空间插值**：每个方向在 7 档半径上测耗时，在 15 分钟两侧的采样点之间线性插值出边界，再平滑成多边形。全程不需要底层路网数据；5、10 分钟内圈用同一批采样插出来，零额外消耗。
- **数据怎么来的**：`scripts/benchmark_api.py` 用本地缓存里百度的真实回答回放，令牌桶、在途上限、重试、缓存都是生产代码，延迟在虚拟时钟上模拟，零配额、可复现。回放的点对数与真实运行逐个对上（桃浦 12 = 12、曹杨 301 = 301），逐格判定与快照 100% 一致。

## 1. 计算策略与优化

### 1.1 用到的接口

| 接口 | 用途 | 代码 |
| --- | --- | --- |
| 批量算路 `routematrix/v2/walking`（另有 riding、driving） | 等时圈采样、中心到网格的耗时（热力）、盲区判定、模拟新建、核验选址 | `baidu/client.py` 的 `route_matrix`、`route_matrix_grid` |
| 步行路线规划 `directionlite/v1/walking` | 补回过街与路口等待、判断路线是否穿过围挡、复测巡检 | `walking_route` |
| 地点检索 `place/v2/search` | 六类民生设施、工地候选；小学用 `scope=2` 取导航点和"出入口"子点，再按校名补查校门 | `search_poi`、`search_poi_all`、`poi/entries.py` |
| 地理编码、逆地理编码、坐标转换 | 地址定位、选址写地址、WGS84/GCJ02 转 BD09 | `geocode`、`reverse_geocode`、`geoconv` |

### 1.2 批量算路怎么装满一个请求

- **单起点多终点**（`route_matrix`）：终点按 100 个一批切开，几批同时发出。
  - 等时圈 36 方向 × 7 档 = 252 点，切成 100 + 100 + 52，共 3 个请求；
  - 中心到圈内网格（桃浦 116 格、曹杨 144 格），各 2 个请求。
- **多起点多终点**（`route_matrix_grid`）：按"起点数 × 终点数 ≤ 100"切成矩形块。
  - 这条限制是 2026-09-15 用 `scripts/probe_matrix_shape.py` 实测出来的：1×100 到 100×1 都正常，101 个点对返回 `status: 2`；
  - 骑行的乘积上限是 50，代码里按出行方式取不同上限。
- **只补缺的点对**（2026-10-03 起）：一组测距先逐个查缓存，把起点按"缺哪几个终点"分组，缺的终点集合相同的起点并成一块，只请求这些矩形。已缓存的点对一个都不重发。
  - 不用"缺口的外接矩形"：那样会把矩形里已缓存的点对一起重发；
  - 叠加用户标注重算时（第二遍），候选顺序变了，同一组里会混着测过和没测过的网格，这一改动正是为它做的。
- **盲区判定用"多起点 × 1 终点"**：把"第 k 近的候选是同一家设施"的网格并成一组，一组一列。点对数等于网格数，请求数等于候选设施数。
- **有校门的小学是"多起点 × 几个终点"**（2026-10-04 起）：一组网格对这所学校的 1~4 个校门各测一次，取最近的。候选排序、直线剪枝也按最近的校门算。校门之间常常只隔 20~30 米，所以校门终点的缓存键按 10 米量化（其余仍是 50 米），避免两个校门共用一个结果。

### 1.3 怎么少用点对（配额按点对计）

| 措施 | 做法 | 效果 |
| --- | --- | --- |
| 只在 15 分钟圈内铺网格 | 100 米一格，圈外不铺；设施检索仍罩住 2.5 公里 | 桃浦 116 格、曹杨 144 格（旧版 1.5 公里 / 200 米是 177 格，大部分在圈外） |
| 直线下界剪枝 | 直线距离是步行距离的下界，直线就超过 1 公里的设施不进候选（有校门的按最近的校门算） | 桃浦 348 个"网格 × 品类"里 246 个零请求完成判定 |
| 够近就停 | 判定"1 公里内有没有"只需找到一家达标的，按由近到远一轮轮测，找到就停 | 曹杨设施密，判定用的 602 个点对（不含中心到各格）比 3 类 × 144 格多 39%，多出的主要是小学一所测 1~2 个校门 |
| 按候选分组装箱 | 同一轮里共用同一候选的网格并成一次请求（N×1，有校门的是 N×校门数） | 曹杨盲区一段：逐对请求要发 18720 个请求，现行发 51 个 |
| 最多 4 轮 | 4 轮还没判定的记"未知"，不无限测下去 | 有上界；曹杨 3 个"格 × 品类"因此记未知 |
| 按点对缓存 | 坐标量化到 50 米，每个点对单独存盘，30 天有效 | 换一个候选集、换一个中心点，测过的点对照样复用 |
| 只补缺的点对 | 见 1.2 | 2026-10-03 重新生成时，桃浦 40 个、曹杨 18 个已缓存的点对没有重发 |
| 同一批采样插多个圈 | 5、10 分钟内圈和"不计过街等待"的外圈都用同一批采样插值 | 0 个额外点对 |
| 纯算法与含标注即时切换 | 结果里带着还原纯算法结果所需的差异，前端切换不重算 | 0 个点对 |
| 首屏走快照 | 打开页面默认展示预生成快照，实时计算要用户显式触发 | 打开即看，零消耗 |
| 分页串行 | 地点检索只有拿到这一页、知道还有下一页才翻页 | 设施少的品类不白烧检索配额 |
| 校门只查一次 | 按校名补查校门最多 30 所、由近到远；结果进检索缓存，查不到就保留已有的导航点，不算品类失败 | 曹杨多 18 次检索、桃浦多 3 次（见 1.4）；重跑 0 次 |
| 按标签剔除误检 | 小学一类按百度的 `classified_poi_tag` 剔除成人教育、培训机构、托管班、幼儿园等 | 曹杨剔除 1 家（进修学院），少测一个候选 |

### 1.4 并发与限速

| 机制 | 设定 | 依据 |
| --- | --- | --- |
| 全局令牌桶 | 8 QPS（`BAIDU_MAX_QPS`） | 4.1：地理编码 12 并发全部成功，16 并发出现 2/16 次 401 |
| 按点对加权 | 每 20 个点对折算 1 个令牌（`PAIRS_PER_TOKEN`）：100 点对的请求约占 0.6 秒的速率预算 | 官方没公开并发的计量口径，这里取保守值 |
| 批量算路在途上限 | 3（`BAIDU_MATRIX_CONCURRENCY`），设为 1 即完全串行 | 回放实验：在途 1 / 2 / 3 / 4 / 6 → 28.9 / 17.5 / 14.4 / 13.1 / 12.6 秒，3 以后收益很小；在途越多，撞上限流时一起退避的请求也越多 |
| 步行路线在途上限 | 4（`BAIDU_ROUTE_CONCURRENCY`） | 实测 8 并发全部成功，12 并发出现 3/12 次 401 |
| 连接复用 | httpx 连接池，keep-alive 120 秒 | `scripts/probe_network.py` 两次链路诊断：新建 1.88 秒对复用 0.92 秒、新建 2.5 秒对复用 0.54 秒（随时段波动），新建连接还偶发 ConnectError |
| 并发发出的环节 | 等时圈的几批矩阵；36 条路线；六类设施与各关键词；各所学校的校门检索；盲区同一轮的各候选组 | 总速率仍由令牌桶封顶 |
| 品类之间串行 | 盲区三类依次判定 | 三类同时跑会让几个大矩阵一起挤令牌桶，更容易撞上并发限流 |
| 进程级共享 | 两道闸门是全进程共享的：多人同时做实时分析，不会把百度接口打到限流，代价是各自变慢 | 样例、导出、健康检查不经过闸门，照常秒回 |

各环节"一个点一个请求 / 串行"和现行做法的对比（回放实验第 3 节，延迟假设 B，桃浦）：

| 环节 | 朴素做法 | 现行做法 |
| --- | --- | --- |
| 等时圈 252 个采样点 | 逐点请求 244 次，1.8 分钟 | 批量 3 次、在途 3，2.3 秒 |
| 过街校正 36 条路线 | 串行 15.3 秒 | 在途 4，4.8 秒 |
| 设施检索（17 个关键词含翻页，另按校名查校门；共 20 次） | 逐个串行 8.3 秒 | 并发 2.8 秒 |
| 同上，曹杨（共 45 次） | 逐个串行 18.4 秒 | 并发 6.0 秒 |

### 1.5 对照实验：盲区判定的五种做法

`scripts/benchmark_api.py`，零配额。同一份设施数据、同一个网格，只换测距的做法（延迟假设 B）：

| 做法 | 桃浦 116 格：点对 / 请求 / 模拟耗时 | 曹杨 144 格：点对 / 请求 / 模拟耗时 | 结论与全量矩阵一致 |
| --- | --- | --- | --- |
| 逐对请求，串行 | 4524 / 4524 / 32.4 分钟 | 18720 / 18720 / 2.2 小时 | 100% / 100% |
| 全量矩阵（不剪枝），串行 | 4524 / 51 / 66.9 秒 | 19584 / 254 / 5.0 分钟 | 基准 |
| 全量矩阵，在途 3 | 4524 / 51 / 30.7 秒 | 19584 / 254 / 2.1 分钟 | 基准 |
| 现行，串行 | 253 / 14 / 8.4 秒 | 746 / 51 / 28.9 秒 | 100% / 99.3% |
| **现行，在途 3（默认）** | **253 / 14 / 6.1 秒** | **746 / 51 / 14.4 秒** | **100% / 99.3%** |

怎么保证这组数可信：

- **回放的是真实回答**：点对、路线、检索结果都取自快照生成时写进 `.cache/` 的百度原始结果；只有朴素做法多测的远处设施在缓存里没有，用"直线 × 实测平均绕行系数"补，它们直线就超过 1 公里，不影响结论。
- **和真实运行对得上**：把真实运行开始前已有的缓存装进回放，现行做法实发桃浦 12、曹杨 301 个点对，与 `api_usage` 记录完全相等（2026-10-03 那一版是 218 = 218、634 = 634）；逐格判定与快照 348/348、432/432 一致。曹杨真实请求比回放多 2 个，是真实网络里的重试。
- **只比相对值**：真实网络比模拟慢，所以只在同一延迟假设下比较不同做法，并用 A / B / C 三档延迟看结论是否稳定：现行 / 全量矩阵 = 9.7% / 4.8% / 4.3%，网络越慢省得越多。2026-10-03 从较少的缓存起步那次，盲区一段桃浦真实 30.1 秒、回放约 6 秒，曹杨真实 38.3 秒、回放约 14 秒。
- **可复现**：固定随机种子，重跑结果不变；整套实验本机 2~4 分钟（视机器负载）。

## 2. 容错与降级

总原则：**接口故障不能伪装成民生结论。** 这个项目的核心输出是"这里缺设施"，所以"没测到"必须和"没有"分开。

### 2.1 状态码分三类处理（`baidu/errors.py`）

| 类别 | 状态码 | 处理 |
| --- | --- | --- |
| 瞬时噪声 | 401、402（并发超限）、1（服务内部错误）；网络错误、JSON 解析失败 | 指数退避重试，最多 3 次。退避时间带 ±50% 随机抖动，几路请求不会同时醒来再撞一次 |
| 配额耗尽 | 302（当日超限）、301（永久超限） | **不重试**。该接口当天直接熔断，之后的调用不再发出；302 在北京时间零点自动解除 |
| 配置错误 | 5、102、200、210、211、220、240、251、260、261 | 不重试，按状态码给出具体原因，比如"后端用了浏览器端 AK""没勾选这项服务""IP 白名单不对" |

**为什么 302 不能重试**：早期版本把 302 当限流重试，每次失败都被放大成 4 个请求（见 4.1）。

**配额错误一路上抛**（2026-10-03 修）：多起点矩阵的分块遇到 302/301 和配置错误不再吞成"这一块测距失败"，而是直接上抛；熔断检查放在计点对之前，熔断后的调用不会虚增点对数。各调用方按自己的语义接住：

- 盲区判定：这一组记"测距失败"，最后判"未知"，警告里写明配额用尽；
- 模拟新建、核验选址：改按直线估算，结果标 `estimate_quota`，写"批量算路配额已用尽，只按直线距离估算"，而不是"若干格未核验"。

### 2.2 每种异常的兜底

| 情况 | 系统的处理 | 用户看到 |
| --- | --- | --- |
| 某类设施检索失败（含某一页失败） | 整类记为"查询失败"。只拿到一半的结果也丢弃，因为半截结果会让设施显得偏少 | 该品类显示"查询失败，数量未知"，不计入评分，不当成缺失 |
| 盲区测距失败 | 该网格的该品类记"未知"，不算盲区；判定成功的格子不到一半的品类，不给盲区占比、不进评分 | 地图上测距失败的格子单独用浅蓝显示，警告里写明有几格没测到 |
| 盲区判定中途配额耗尽 | 熔断后剩下的组不再发请求，没测到的记"未知" | 警告写明配额用尽、何时恢复 |
| 等时圈采样有整批失败 | 不出等时圈（`IncompleteSamplingError`），返回失败原因和建议 | "等时圈采样有 N 批批量算路失败：……"；不会画出一个缩水的圈并照常出分 |
| 热力那一步配额耗尽 | 各格耗时记"未知"，盲区判定照常尝试 | 热力缺失，其余照常 |
| 模拟新建、核验选址时配额耗尽 | 改按直线估算，标 `estimate_quota` | "批量算路配额已用尽，只按直线距离估算……" |
| 步行路线失败 | 该方向退回批量算路的耗时，并标注"未校正" | 警告里写明几个方向没取到路线 |
| 驾车实时路况失败 | 用过期的路况缓存兜底，并写明是多久以前的路况；只要有一个点没有旧数据就放弃，不混用 | "路况为 N 分钟前的数据" |
| 单次分析超时（240 秒） | 中止，返回停在哪一步、已完成哪几步 | 已经推送的等时圈、设施结果保留在页面上（SSE 渐进推送） |
| 生成快照时配额中途用完 | `run_isochrone.py` 不覆盖原快照，另存 `.partial.geojson` | 命令行写明哪一步中断 |
| 没配服务端 AK | 后端照常启动；样例、离线模拟、导出照常可用 | 实时计算时提示怎么配 AK |
| 当天配额耗尽 | 熔断该接口；错误信息给出兜底办法：打开样例（零消耗）、重算已算过的地点（命中缓存）、切换离线模拟 | "批量算路今天的配额已经用完，北京时间次日 0 点自动重置" |
| AK 完全不可用 | 离线模拟模式：按中心坐标生成确定的伪随机结果 | 页面明确标注"离线模拟，不代表真实路网" |

故障注入（回放实验第 6 节，曹杨圈内 144 格的盲区一段；无故障时 746 个点对、51 个请求、3 个"未知"）：

| 注入的故障 | 收到请求（含重试） | 结论一致 | 未知 | 误判为盲区 |
| --- | --- | --- | --- | --- |
| 10% 的请求返回 401 | 59 | 100% | 3 | 0 |
| 30% 的请求返回 401 | 81 | 98.4% | 10 | 0 |
| 5% 的请求网络中断 | 53 | 100% | 3 | 0 |

| "药店"检索一律失败 | — | 66.7% | 147 | 0 |

不一致的判定全是"已判定 → 未知"，没有一格翻成相反的结论。配额那一组：收到 302 的 3 个请求都是熔断前已经发出的，熔断后新发出的批量算路请求为 0。

实测：2026-09-27 对桃浦做复测巡检，共 40 次请求，其中 4 次是撞上限流后的自动重试。36 个方向全部取到，用时 12.9 秒。

### 2.3 消耗可追溯

- 客户端分接口统计实发请求数（含重试）、实发点对数（命中缓存的不计）、整块失败的矩阵请求、路线失败、配额事件。
- 每次分析在调用前后取差，得出"本次"消耗；`scripts/run_isochrone.py` 按环节（等时圈、设施、盲区）写进快照的 `properties.api_usage`。

## 3. 空间插值：不拿底层路网，推出可达范围

### 3.1 扇形采样 + 射线插值（`isochrone/algorithm.py`）

1. 从中心向 36 个方向（每 10°）各放 7 个采样点。
   - 步行半径为 200 / 400 / 600 / 800 / 1000 / 1200 / 1400 米；
   - 骑行、驾车用各自更大的半径梯度，避免整圈饱和。
2. 252 个点一次批量算路，得到真实路网耗时。
3. 每个方向从内往外扫：
   - 找到第一个超过 15 分钟的点，在它和前一个点之间**线性插值**出边界半径；
   - 某点不可达（或同方向路线穿过用户标注的围挡），视为障碍，边界停在上一个可达点，标"障碍截断"；
   - 扫到最外仍未超时，标"饱和"，表示真实边界可能更远。
4. 36 个边界半径做环形滑动平均（窗口 3），连成多边形，算面积。
5. 用同一批采样再插出 5 分钟、10 分钟内圈：**零额外请求**。

### 3.2 过街等待校正（`isochrone/refine.py`）

- **发现问题**：2026-09-24 在曹杨实测，步行批量算路的耗时恒等于距离 ÷ 约 1.17 m/s，14 组点对的速度全在 1.17~1.18 m/s 之间，**完全没有算路口等待**。
- **做法**：每个方向取一条步行路线规划，每一段实际耗时超出匀速步行的部分，就是等待时间，沿路线累积成"距离 → 等待"曲线，补到这个方向每个采样点的耗时上。
- **效果**：
  - 曹杨每公里约多出 82 秒，圈从 1.75 km² 缩到 1.41 km²；
  - 桃浦每公里约多出 36 秒，圈从 1.32 km² 缩到 1.18 km²。

### 3.3 热力图也是插值，不是密度图（`frontend/src/lib/heatRaster.ts`）

- 网格耗时先栅格化成"一格一像素"的小图，放大绘制，由浏览器做双线性插值；
- 网格只铺在 15 分钟圈内，颜色只在实测过的格子之间过渡，不会在没测过的地方染色；
- 网格耗时的过街等待，用相邻两条射线的校正曲线按角度加权得到。

### 3.4 为什么等时圈不铺满网格测

1.5 公里范围铺 50 米网格要约 2800 个点，比扇形采样的 252 个多一个数量级，而日配额只有约 2500 个点对。扇形采样在边界附近点最密，正好是求边界最需要的地方。盲区判定的 100 米网格是在等时圈求出来之后、只在圈内铺的。

### 3.5 局限（被问到时如实说）

- 36 个方向之间相隔 10°，在 1 公里处两条射线相距约 175 米。夹在两条射线之间的窄通道或窄障碍可能测不到。方向数可以在 8~72 之间调。
- 耗时随半径不单调时（比如绕过河后又变近），取"第一次超时"作为边界，更外侧的可达点不算进圈。
- 环形平均会把某个被障碍截断的方向向外拉一点，这是平滑和保真之间的取舍。

## 5. 已修的问题与剩下的不足

### 已修（2026-10-03）

1. **矩阵块缓存不完整时整块重发。** 原来 `_matrix_block` 只要块里有一个点对没缓存，就把整块重新请求。现在 `route_matrix_grid` 先查缓存，按"缺的终点集合"给起点分组，只请求缺的那几块（见 1.2）。单元测试覆盖了"测过的起点不重发""按缺的终点分组""配额耗尽时已测到的块照样入缓存""熔断后零请求、不计点对"。
2. **"配额用完改用直线估算"的分支走不到。** 原来 `_matrix_block` 把 `QuotaExhaustedError` 吞成"测距失败"，模拟新建只会显示"若干格未核验"。现在配额和配置错误直接上抛，盲区判定在自己那一层接住记"未知"，模拟新建与核验选址走到 `estimate_quota`（见 2.1）。回放实验里也验证了这条路径。
3. **文档和代码对不上**：README 的"矩阵串行""品类串行的理由"、配额申请材料里的旧网格估算、`poi/construction.py` 的"每天约 150 次"、代码注释里并发数据的出处、连接复用的两组数字，都已改正或注明出处。
4. **缺"显著降低耗时"的对比数据。** 新增 `scripts/benchmark_api.py` 和 `reports/api-benchmark.md`：两个样例 × 两种网格 × 五种做法，外加各环节、在途数、延迟假设、故障注入，共几十组。
5. **盲区只在 15 分钟圈内判定。** 圈内 100 米网格（桃浦 116 格、曹杨 144 格）；旧快照载入时自动截到圈内。之前的估算是桃浦约 480、曹杨约 830 个点对起，缓存为空时实测 491、888（小学改按校门之前），估算偏乐观约 2%~7%。

### 已改（2026-10-04）

- **小学测到坐标点，而不是校门。** 学校有面积，坐标点常在校园中间，批量算路把它吸附到最近的路上，那条路可能贴着围墙、没有门。现在小学按最近的入口测距（见 0 节、1.2 节），入口是导航点加"出入口"子点（停车场出入口不算），20 米内并成一个，每校最多 4 个；取不到入口的学校仍按坐标点。药店是沿街铺面、菜场没有测距，所以只改小学一类。直线对照实验（`scripts/compare_straight_line.py`）仍用坐标点，保持和以前的对照口径一致。
- **一个缓存粒度不够用。** 50 米量化会把相隔二三十米的两个校门并成同一个缓存键，后测的那个直接拿到前一个的结果。校门终点改按 10 米量化，其余点对仍是 50 米，旧缓存照常命中。
- **"只测到一部分校门"不能当成结论。** 某所学校的校门有的没测到、测到的又都超过 1 公里时，不能断言这所学校走不到；别的候选也都不达标时，这一格记"未知"，不判盲区。
- **检索误检。** 小学关键词会搜到进修学院、培训机构，现在按百度的分类标签剔除（曹杨剔除 1 家）。

### 还可以改

6. **客户端不分原因记重试。** 曹杨重新生成时比回放多出 2 个请求（2026-10-03 那次多 19 个），只能推断是重试，分不出是 401 限流还是网络重连。按状态码记一份重试计数写进 `api_usage`，下次真实运行就能看清。
7. 等时圈的 252 个采样点里，最内一圈（200 米）有 8 个和邻点落进同一个 50 米缓存格，批量请求时各算一次。发请求前按缓存键去重，每次能省 8 个点对（约 3%）。
8. 盲区三个品类改为并发判定。每个品类最多 4 轮往返，串行是 12 轮，并发是 4 轮，总速率仍由令牌桶兜住。可以先在回放实验里加一组量收益，再决定改不改。
9. 状态码 101（服务未开启）、4（配额校验失败）没有归类，现在会显示成笼统的上游错误，应该补进配置错误或配额类。
10. 地理编码、坐标转换的结果没有缓存。同一个地址反复搜索会重复消耗地理编码配额，好在这项配额不紧。
11. 网络整体中断或 401 连续出现时，没有短时冷却：每个请求各自重试 3 次，直到 240 秒超时。可以加一个"连续失败 N 次后暂停几秒"的断路器。
12. 非流式接口 `/api/isochrone` 出错时不返回部分结果，只有流式接口保留。前端用的是流式，影响不大。

## 6. 答辩可能被问到的问题

**问：你们用了批量距离矩阵吗？怎么用的？**
所有测距都用批量算路。等时圈 252 个采样点 3 个请求；中心到圈内一百多个网格 2 个请求；盲区判定把共用同一候选设施的网格并成"多起点 × 1 终点"，一个请求装满 100 个点对。单请求的形状上限是我们自己探测出来的：起点数 × 终点数 ≤ 100。

**问：大量 POI 怎么避免算爆？**
三条：直线距离是步行距离的下界，直线超过 1 公里的直接排除；找到一家达标的就停；按候选分组装箱。曹杨盲区判定 746 个点对，每格对每家都测要 19584 个；结论 99.3% 一致，其余记"未知"，没有一格判反。再加上按点对缓存、补测只请求缺的点对，同一地点重跑零消耗。

**问：省了多少时间？数据怎么来的？**
用本地缓存里百度的真实回答回放，生产代码原样跑，延迟在虚拟时钟上模拟，零配额。回放的点对数和真实运行逐个对得上。曹杨盲区一段：逐对请求 2.2 小时、全量矩阵 5.0 分钟、现行 14.4 秒；三档延迟假设下现行都只要全量矩阵的 4%~10%。

**问：并发怎么控制？会不会被限流？**
令牌桶钳住总速率 8 QPS，大请求按点对数多占令牌；批量算路最多 3 个在途、路线最多 4 个。8 QPS 和路线的 4 来自我们对并发上限的实测，留了余量；在途 3 是回放实验里收益开始变平的地方。撞上 401 会带随机抖动退避重试，注入 30% 的 401 也没有一格判反。

**问：配额用完了怎么办？**
302、301 不重试，该接口当天熔断，零点自动解除，错误一路上抛到调用方：盲区判定把没测到的格子记"未知"，模拟新建改按直线估算并写明"配额已用尽"。页面写明是哪个服务、什么时候恢复，并给出三条退路：打开样例、重算已算过的地点（走缓存）、切换离线模拟。

**问：POI 检索失败，会不会被当成没有设施？**
不会。任何一页失败，整类就标"查询失败、数量未知"，不计分、不当成缺失；只拿到一半的结果也丢掉。测距失败的网格同样记"未知"，不算盲区。故障注入里"药店"检索失败，医药 144 格全部记"未知"，误判为盲区 0 格。

**问：等时圈怎么来的？你们有路网数据吗？**
没有。36 个方向各 7 个采样点用批量算路测耗时，每个方向在 15 分钟两侧的采样点之间线性插值出边界，遇到走不通的点就截断，再环形平滑。5、10 分钟内圈用同一批数据插出来，不再请求。

**问：批量算路的耗时准吗？**
不含红绿灯。我们实测它恒等于距离 ÷ 1.17 m/s，所以每个方向另取一条步行路线，把路线里超出匀速步行的秒数补回去。曹杨的圈因此从 1.75 缩到 1.41 km²。

**问：一次分析要多久、花多少？**
缓存为空时桃浦 486 个点对、曹杨 982 个，外加 36 次路线、20~45 次检索（含按校名查校门）；同一地点重跑 0 个点对。2026-10-03 重新生成快照，真实耗时桃浦 35.5 秒、曹杨 44.1 秒（只有盲区一段要请求）。首屏默认打开预生成快照，零消耗。

**问：学校那么大，测到哪个点？**
测到最近的校门。地点检索加 `scope=2` 会给导航点和学校的各个"出入口"子点，我们取这些点（停车场出入口不算，20 米内的并成一个，每校最多 4 个），网格到这所学校的距离取到最近那个门的步行距离。曹杨对照实验里，按坐标点算缺小学 26 格，按校门算 18 格；其中 10 格是门开在居民这一侧、按点被算远了，另有 2 格反过来，坐标点吸附到的路贴着围墙、并没有门。
