# 百度地图 API 能力边界探测报告

- 探测日期：2026-09-11
- 账号类型：个人开发者，服务端 AK（免费基础服务）
- 探测脚本：`scripts/probe_quota.py`、`scripts/probe_network.py`、`scripts/probe_endpoint.py`

本报告用于确定后端调度器的限流参数、批量粒度与重试策略。结论已同步至 `.env`。

> **测量方法说明**：早期几轮数据因探测进程被意外重复启动、多实例并行而严重失真——
> 配额探测有 2 个实例并行（表现为大量 20 秒超时），选址脚本有 5 个实例并行长达 18 分钟
> （直接烧光了地点检索的日配额）。本报告采用的是确认单进程独占后重跑的结果。
>
> **方法论教训**：对配额受限的 API 做探测，必须先确认没有同类进程在跑。
> 多实例并行既会污染并发与延迟的测量，又会成倍消耗不可再生的日配额。
> 建议探测脚本自带单实例锁。

## 一、接口连通性

五个接口全部可用。

| 接口 | 路径 | 状态 | 典型延迟 |
| --- | --- | --- | --- |
| 地理编码 | `/geocoding/v3/` | 正常 | 0.35s |
| 地点检索（周边） | `/place/v2/search` | 正常 | 0.6s |
| 批量算路（步行） | `/routematrix/v2/walking` | 正常 | 0.4s |
| 步行路线规划 | `/directionlite/v1/walking` | 正常 | 0.4s |
| 行政区划检索 | `/api_region_search/v1/` | 正常 | 0.35s |

> **踩坑记录**：行政区划检索的关键词参数名是 `keyword`，不是其他检索接口通用的 `query`。
> 传 `query` 会得到 `status: -1, message: "keyword is empty!"`，容易误判为接口未开通。

## 二、批量算路单次终点数上限

**上限为 100 个终点**（1 起点 × 100 终点）。二分查找结果：

| 终点数 | 结果 |
| --- | --- |
| 60 / 90 / 97 / 98 / 100 | 成功 |
| 101 / 105 | `status: 2` 请求参数非法 |

超限返回参数错误（2）而非配额错误，说明这是接口的硬性参数约束，与账号等级无关。

**对算法的意义**：等时圈采样点可按 100 个一批提交。36 方向 × 5 档半径 = 180 个点只需 **2 次请求**；
加密到 48 方向 × 6 档 = 288 个点也只要 **3 次请求**。采样密度不再是瓶颈，可以放心提高等时圈精度。

## 三、并发上限

预热连接池后逐级加压，各接口触发限流的档位：

| 接口 | 全成功的最高并发 | 首次触发限流 |
| --- | --- | --- |
| 地理编码 | 12 | 16（2/16 被限） |
| 步行路线规划 | 8 | 12（3/12 被限） |
| 地点检索 | — | 见第四节，低速率下即有偶发 302 |
| 批量算路 | — | 数据不可用，见下方说明 |

**批量算路的并发数据本轮不可信。** 它在并发 2 就报限流，但那紧接在 12 并发的连接池预热之后，
是余波污染。冷却后单独复测，8 次串行连发全部成功，实测吞吐约 2.1 次/秒。
脚本已把换接口的冷却时间从 3 秒调到 15 秒，后续重跑可得到干净数值。

**建议安全 QPS 取 8**，即观测到的最低确切限流档位（12）之下留三分之一余量。

## 四、关键发现：地点检索的日配额才是项目的真正瓶颈

这是本次探测最重要的结论，也订正了本报告早先版本的一处误判。

### 4.1 302 是真实的日配额耗尽，且按接口独立计算

早先观察到 302 零星出现、后续请求又能成功，据此判断它是"瞬时噪声、可重试"。
**这个判断是错的。** 地点检索的 302 最终变为持续返回，且同一时刻其他接口完全正常：

| 接口 | 同一时刻的状态 |
| --- | --- |
| 地理编码 | `status: 0` 正常 |
| 批量算路 | `status: 0` 正常 |
| 步行路线规划 | `status: 0` 正常 |
| **地点检索** | **`status: 302` 天配额超限** |

所以 302 确实是"当日配额耗尽"，且**每个接口的额度独立计算**。
早先看到的间歇性 302，是配额接近上限时的波动，不是节点计数噪声。

### 4.1.1 实测：地点检索的免费日配额约 150~160 次

这是全项目最重要的一个数字，在单实例受控条件下测得。

2026-09-13 配额重置后的**当日首次运行**，单实例、无并行、且代码已改为不对 302 重试
（排除了请求放大），选址脚本在**第 156 次实发请求**后触发 302：

```
地点检索 156 次实发，0 次命中缓存（命中率 0%）
[中断] 地点检索返回 302：天配额超限，限制访问
```

同期批量算路与地理编码的调用量远超此数（单次等时圈即提交 252 个点对）却毫无问题。
因此可以确认：**地点检索的免费日配额约 150~160 次，比其他接口小一到两个数量级。**

> **一处反复订正的说明**：本报告 09-11 版本先提出"地点检索额度远小于其他接口"，
> 随后因发现选址脚本曾被误启动 5 个实例并行运行（聚合约 40 QPS，且当时对 302 也重试，
> 把请求量放大约四倍）而认为样本不可比、撤回了该推论。09-13 的受控复测表明，
> **原推论方向正确，撤回过头了**。并行事故确实污染了当时的数据，但不改变结论本身。

### 4.1.2 架构影响：POI 必须走快照，不能走实时

日配额 150 次意味着：

- 一次完整体检若对每个网格点实时检索，配额撑不过一个社区；
- 评审方连续演示两三次就会耗尽，系统直接瘫痪；
- 开发期的调试同样会被配额卡死。

因此 POI 层必须设计为**一次性采集 + 快照落盘 + 仓库随源码分发**，应用默认读快照，
实时检索仅作为可选的增量刷新。这与交付要求中"配置好示例数据，保证评审方能快速跑通演示"
的要求正好一致——不是权宜之计，而是本就该有的工程做法。

### 4.1.1 对 302 重试是配额的自杀行为

这次耗尽事件里，"302 也重试"的逻辑把每次失败放大成四次请求。配额越接近耗尽，
302 出现越频繁，重试放大得越狠——形成正反馈，在最后阶段急剧加速额度消耗。

这也是把 301/302 与 401/402 区分处置的**实证理由**，而不只是语义上的讲究。

### 4.2 401 仍然是瞬时噪声，需要退避重试

与 302 不同，`status: 401`（并发超限）确实是可恢复的瞬时现象。
批量算路终点数的二分查找中出现过这一幕：

```
 97 个终点 -> status=0    成功
 99 个终点 -> status=401  当前并发量已超过约定并发配额   <-- 单发请求，谈不上"并发"
 98 个终点 -> status=0    成功
```

99 个终点是一次孤立的串行请求，却报并发超限，而前后的 97、98、100 都正常。
说明 401 反映的是百度侧某个节点的瞬时计数策略，与请求本身的合法性无关。

### 4.3 错误码分类处置

| 类别 | 状态码 | 处置 |
| --- | --- | --- |
| 瞬时噪声 | `401` `402`、网络异常 | 指数退避重试 3 次 |
| 配额耗尽 | `301` `302` | **立即终止该接口调用**，重试无意义；切换缓存或降级模式 |
| 配置错误 | `200` `210` `220` | 终止并告警，属于部署问题 |

把 302 混进重试集合会白白浪费退避时间；反过来把 401 当致命错误又会在额度充足时误降级。
这个分寸正是评分细则里「容错与降级机制」要考察的点。

### 4.4 绝不能用 0 表示查询失败

选址脚本最初把检索失败记为 `-1`，统计时又用 `if c > 0` 过滤，等价于把失败当成"该品类 0 个设施"。
配额耗尽后，望京这种配套极密集的区域被统计成六个品类全部为 0——**API 故障被伪装成了服务盲区**。

这类错误在本项目中格外危险，因为系统的核心输出就是"这里缺设施"。必须严格区分
「查到了，确实是 0」与「没查到」：后者用 `None` 表示，不参与评分，并在报告中显式标注为数据缺失。

## 五、连接复用：有收益，但不是瓶颈

对照实验（`probe_network.py`，单进程独占环境）：

| 实验 | 成功率 | p50 延迟 |
| --- | --- | --- |
| 串行 + 复用连接 | 7/8 | **0.92s** |
| 串行 + 每次新建连接 | 5/5 | **1.88s** |
| 并发 3 / 5 / 8 / 12 + 共享连接池 | 全部 100% | 2.0 ~ 2.6s |

复用连接约省 1 秒，相当于一次 TLS 握手的开销，**约 2 倍提速**。值得做——一次体检要发一二十个请求，
省下十几秒是实打实的——但它属于常规优化，不是性能命门。

> **一处订正**：早先一版报告称复用连接快 5 倍、且新建连接会随机 `ConnectError`，据此把连接池
> 说成"能否跑通的前提"。那是在两个探测进程并行的污染环境下测得的，结论过重。干净环境下新建连接
> 5/5 全部成功，反倒是复用连接那组出现了 1 次 `ConnectError`——可见偶发连接错误与是否复用无关，
> 属于链路本身的抖动。真正造成早期 20 秒超时的是重复启动的并行进程，不是 TLS 握手。

## 六、写入 .env 的参数

```env
BAIDU_MAX_QPS=8
BAIDU_MATRIX_BATCH_SIZE=100
BAIDU_HTTP_TIMEOUT=30
BAIDU_MAX_RETRIES=3
BAIDU_RETRY_BACKOFF=0.5
```

配套的调度器要求，按重要性排序：

1. **POI 持久化缓存/快照** —— 地点检索日配额是全项目的硬约束，必须把检索结果按
   50m 网格量化后落盘复用，并为演示预生成离线快照。这是硬性需求，不是优化项。
2. **错误码分类处置** —— `401/402` 退避重试；`301/302` 立即终止并切缓存；`200/210/220` 告警。
3. **失败与零值严格区分** —— 查询失败一律用 `None` 表达，绝不退化成 0。
4. **令牌桶限流** —— 全局出口限速 8 QPS，所有接口共用一个桶。
5. **共享连接池** —— 进程级单例 `AsyncClient`，`keepalive_expiry` 不低于 120 秒，省一次握手。

> 探测值为 2026-09-11 当次快照，受账号等级与当日剩余配额影响。运行时仍需依赖退避重试
> 与降级兜底应对波动。
